## Storage & Docker Safety Rules

This machine has a limited ~153 GB root filesystem. Be extremely conservative with disk usage.

1. NEVER create large temporary files, datasets, model artifacts, Python environments, Docker build contexts, or caches without first checking available disk space.

2. Before building Docker images:
   - Check `df -h /`
   - Check the project size with `du -sh .`
   - Inspect `.dockerignore`
   - NEVER send `storage/`, generated model environments, `.venv/`, `node_modules/`, `.git/`, caches, datasets, or other large development artifacts into a Docker build context unless they are explicitly required.

3. For MODEL_DEPLOYER specifically:
   - `storage/` is MinIO/object storage and may contain large model artifacts.
   - `storage/envs/` contains generated model-specific Python environments.
   - NEVER copy `storage/` or `storage/envs/` into Docker build contexts.
   - Docker containers should access required storage through the intended volume/mount/object-storage mechanism.
   - Do not duplicate the storage directory into temporary build directories.

4. Before creating multiple test models/environments:
   - Estimate the total disk usage.
   - Do not create dozens of independent environments blindly.
   - Reuse a base environment where appropriate.
   - Clean up temporary test environments after testing.
   - Keep a clear distinction between persistent model artifacts and disposable test environments.

5. NEVER run `rm -rf` on Docker's internal directories such as `/var/lib/docker` while Docker is running.
   - Do not manually delete Docker's `overlay2`, `containers`, `volumes`, or other internal directories.
   - For Docker cleanup, use Docker commands such as `docker image prune`, `docker container prune`, `docker volume prune`, or `docker system prune` only after checking what will be removed.

6. NEVER leave abandoned Docker build contexts or temporary build artifacts on disk.
   - If a build fails or is interrupted, inspect and clean up temporary artifacts safely.
   - Do not start another large build if the previous build has left significant temporary data behind.

7. Before any operation expected to generate >1 GB:
   - Check available disk space.
   - Tell me how much space the operation is expected to consume.
   - If free space is insufficient, STOP and ask me before proceeding.

8. After large builds/model generation:
   - Run `df -h /`
   - Check Docker usage with `docker system df`
   - Check project/storage usage with `du -sh`
   - Clean disposable artifacts.

9. Do not silently generate 10–20 large ML environments/models just to test something.
   Start with 1–2 representative models, validate the workflow, then scale the test.

10. If disk usage suddenly increases by >5 GB during an operation, STOP the operation and report:
   - what was created
   - where it was created
   - current disk usage
   - whether the data is disposable or persistent

11. Protect user data above all else. When unsure whether something is disposable, DO NOT delete it. Ask first.

12. Before Docker builds, always verify that `.dockerignore` excludes at minimum:
   `.git`
   `.venv`
   `venv`
   `node_modules`
   `__pycache__`
   `.pytest_cache`
   `storage/envs`
   `storage`
   large datasets
   generated model artifacts
   logs
   temporary files

The goal is to prevent duplication of large directories and prevent automated experimentation from exhausting the filesystem.
